Slide 09 of 24 Approach 1: Hashing

Approach 1: Encryption Logic (SHA-1 Hashing Mechanics)

Directly reflecting Section 5.1 of Bunny's whiteboard: The long URL is passed to a cryptographic hashing algorithm (SHA-1 or MD5), and the first 6 or 7 characters are extracted as the short code.

FIGURE 9.1: Encryption logic round-trip calculation from Section 5.1 of Bunny's whiteboard.
⚙️ Hash Extraction Flow

1. Input: https://www.facebook.com/anindya.s.dasgupta/
2. SHA-1 generates 40 hexadecimal characters (160 bits):
d3e8f9a2b1c4e5f6a7b8c9d0e1f2a3b4c5d6e7f8
3. Take first 7 characters: d3e8f9a.
4. Latency: SHA-1 computation takes 1ms; DB round trip takes 5ms-15ms.

💎 The Deduplication Benefit

Because cryptographic hashing is deterministic, hashing the exact same URL twice always yields the exact same hash. If two users attempt to shorten the same long link, the system returns the existing short link, saving storage space.

Slide 10 of 24 Collision Cascade

Approach 1 Failure: Hash Collision & Latency Cascade

Here is the fundamental flaw Bunny explains on the whiteboard: Truncating a 40-character hash down to 6 characters inevitably causes Birthday Paradox collisions, triggering an expensive database retry loop.

1. Input: https://www.facebook.com/anindya.s.dasgupta/ ──▶ Hash: 9191c037d0c5f4408f0caf5c3cd39edd...
2. Input: https://www.amazon.in/ ──▶ Hash: 9191c037d0c5f4408f0caf5c3cd39e3rd...
💥 BOTH TRUNCATE TO "9191c0" ──▶ DATABASE PRIMARY KEY COLLISION!
FIGURE 10.1: Verbatim collision example from Bunny's whiteboard. Two completely different websites share the identical 6-character prefix.
⏱️ The Compounding Latency Cascade

When a collision occurs, the database throws a duplicate key error. The server must append a salt or timestamp, re-hash, and re-query the database:
• Attempt 1 (No collision): 1ms encrypt + 15ms DB = 16ms
• Attempt 2 (1 Collision): 16ms consumed + 16ms retry = 32ms
• Attempt 3 (2 Collisions): 32ms + 16ms retry = 48ms
As the database reaches hundreds of millions of rows, collision probability explodes, violating our SLA!

📊 Mathematical Probability Formula

With $k=7$ hexadecimal characters ($16^7 = 268 ext{M}$ space), the collision probability formula is: P(collision) ≈ (n²) / (2 × 16^k) At 1 Million URLs, collision probability is ~0.002%. But at 10 Million URLs, it jumps to 0.2%. At 1 Billion URLs, collisions happen on almost every request!

Slide 11 of 24 Approach 2: Counters

Approach 2: Counter-Based Generation & Monolith Wall

Instead of hashing unpredictable text strings, what if the server uses an auto-incrementing counter (1, 2, 3, 4...)? Each request gets a unique integer, dropping DB collision scans completely!

⚡ Why Counters Slash Latency to 6ms

Request 1 receives ID 1. Request 2 receives ID 2. Because numbers strictly increment, duplicates are mathematically impossible! We no longer need to execute a 10ms database scan. Latency drops from 16ms to just 6ms (local increment + DB save).

🧱 The Monolith Scaling Wall

This single counter works flawlessly on a single monolithic server. But our non-functional requirement specifies 100 Million DAU! A single machine cannot handle this throughput. We must scale horizontally with microservices.

Vertical Scaling (Bigger RAM/CPU) ❌ DOES NOT SCALE TO 100M USERS
▼ MUST USE HORIZONTAL MICROSERVICE REPLICATION ▼
Horizontal Scaling (Multiple App Servers behind Load Balancer)
Slide 12 of 24 Concurrency Failure

Approach 2 Flaw: Load Balancer & Local Counter Collisions

When we deploy multiple server instances (Server 1, Server 2, Server 3) behind a Round-Robin Load Balancer, a catastrophic concurrency bug appears: each server maintains its own local counter.

FIGURE 12.1: When servers boot independently, their local counters all start at 0, corrupting database uniqueness.

The Failure: Server 1 gets request 1 and returns 0. Server 2 gets request 2 and also returns 0! The database crashes with a duplicate key violation. Local in-memory counters cannot exist in distributed architectures.

Approach 2.5: Centralized Redis Counter & Workload Split

This diagram mirrors Section 5.2 of Bunny's whiteboard: Introducing a central Redis counter (2ms-3ms) and separating servers into Encryption (20% workload) vs Decryption (80% workload).

⚖️ 20% Write vs 80% Read Workload

If the Redis counter node goes down or network partitions, all URL creation stops! If you deploy multi-node Redis clusters, synchronizing distributed counters across nodes recreates the exact split-brain duplicate problem we tried to avoid.

Slide 16 of 24 Snowflake ID Math

The 64-Bit Snowflake ID: Exact Binary Math

This slide breaks down the exact mathematical formulas written at the bottom of Bunny's whiteboard. With time, worker ID, and a local sequence combined, 100% collision-free uniqueness is achieved in CPU registers.

FIGURE 16.1: Complete 64-bit binary layout of the Twitter Snowflake ID format.
41-Bit Timestamp Math
2^41 / (365 * 24 * 60 * 60 * 1000L) = 69.73 Years

Provides nearly 70 years of unique, monotonically increasing IDs before timestamp rollover.

10-Bit Worker ID Math
2^10 = 1,024 Workers

ZooKeeper can coordinate up to 1,024 concurrent app server instances running in parallel without conflict.

12-Bit Sequence Math
2^12 * 1000 = 4,096,000 IDs/sec

Each single server can emit 4,096 IDs per millisecond (over 4 Million IDs per second per node!).

The Latency Breakthrough: Generating a Snowflake ID requires 0ms network round-trip time. It is computed in CPU registers in less than 1 microsecond!

Slide 17 of 24 Encoding Pipeline

Base62 Encoding: Converting 64-bit Integers to Clean Web Slugs

Why Base62 dominates URL shortening over Hex and Base64, and the exact radix-conversion algorithm.

Why Base62? Character Space Comparison

Computers store Snowflake IDs as 64-bit binary integers (e.g., 1537228672093888512). Displaying a 19-digit number in an SMS or tweet wastes space. We encode it into an alphanumeric representation:

Encoding Base Alphabet Character Set URL Safe? Capacity at 7 chars
Hexadecimal 16 0-9, a-f Yes $16^7 = 268.4\text{ Million}$ (Too small!)
Base64 64 0-9, a-z, A-Z, +, / No (+ and / need %-escaping) $64^7 = 4.39\text{ Trillion}$
Base62 (Winner) 62 0-9 (10) + a-z (26) + A-Z (26) 100% URL-Safe (No escaping) $62^7 = 3.52\text{ Trillion}$ (Huge headroom!)

Radix-62 Conversion Arithmetic

Base62 conversion is identical to converting base-10 decimal to binary, but using modulo 62 division repeatedly:

python • base62_encoder.py O(log62 N) 
ALPHABET = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ"

def encode_base62(num: int) -> str:
    if num == 0:
        return ALPHABET[0]
    chars = []
    while num > 0:
        num, rem = divmod(num, 62)
        chars.append(ALPHABET[rem])
    return "".join(reversed(chars))

def decode_base62(short_str: str) -> int:
    num = 0
    for char in short_str:
        num = num * 62 + ALPHABET.index(char)
    return num

# Snowflake ID: 1537228672093888512 => '4kycpo' (from whiteboard!)

Slide 18 of 24 Wire Protocol

HTTP 301 vs HTTP 302: The Critical Architecture Tradeoff

Understanding client-side caching, server load reduction, and the sacrifice of analytics tracking.

HTTP 301: Moved Permanently

Browser Caches Indefinitely

The browser caches the redirect mapping permanently in its local disk/memory cache.

  • ✓ Server Load Reduced: Subsequent clicks never touch our servers or load balancers.
  • ✓ Fastest User Experience: Zero network round-trip latency to shortener on repeat visits.
  • ✗ Zero Analytics: We CANNOT track click counts, user geolocation, or referrer after the first visit!
  • ✗ Cannot Revoke or Expire: If the destination changes or URL expires, cached browsers keep redirecting to old URL.
HTTP/1.1 301 Response Wire Trace 
HTTP/1.1 301 Moved Permanently
Location: https://www.facebook.com/anindya.s.dasgupta/
Cache-Control: public, max-age=31536000
Date: Mon, 19 Oct 2026 10:00:00 GMT

HTTP 302 / 307: Found (Temporary)

Industry Standard for Analytics

The browser redirects immediately but does not cache the mapping permanently.

  • ✓ 100% Click Tracking: Every single click hits our decryption server, allowing precise analytics.
  • ✓ Full Expiration Control: When URL expires, we immediately return 410 Gone without stale client caches.
  • ✓ Malware Revocation: We can instantly block malicious URLs reported by Safe Browsing.
  • ⚠ Higher Infrastructure Cost: All 80,000 read QPS must hit our edge load balancer and Redis cache.
HTTP/1.1 302 Response Wire Trace 
HTTP/1.1 302 Found
Location: https://www.facebook.com/anindya.s.dasgupta/
Cache-Control: no-cache, no-store, must-revalidate
Date: Mon, 19 Oct 2026 10:00:00 GMT
⚠️ WHITEBOARD VERBATIM VERDICT: Which one does Bitly use?
Bitly uses HTTP 301 for pure URL redirection performance, but appends tracking cookies or query parameters on first visit! However, modern marketing URL shorteners (like Dub.co or TinyURL analytics tier) utilize HTTP 302 or 307 because click analytics, geolocation telemetry, and real-time link editing are the core monetization features of paid shortener tiers.

Slide 20 of 24 Expiration

Dual-Layer Expiration: Eliminating Zombie Records

Why relying solely on Redis TTL or active scans will crash your database or leak expired links.

The Flaw of Single-Layer Expiration

Checking expires_at < NOW() on every read or running massive DELETE queries causes fatal system failures:

  • ✗ Redis Eviction Failure: Redis is only a cache. If an expired link isn't in Redis, a query falls back to Postgres. Expired links stay live forever!
  • ✗ Massive DELETE Locks: Running DELETE FROM urls WHERE expires_at < NOW() locks the B-Tree table, halting reads and writes for minutes!

The Production Dual-Layer Architecture

We combine Lazy Passive Expiration with Asynchronous Chunked Batch Cleanup:

Layer Mechanism Latency / Load
Layer 1: Lazy (Inline) On cache/DB hit, check expires_at < now(). If expired, return 410 Gone and trigger async delete. 0 ms extra latency. Zero dead links served.
Layer 2: Daily Cron (Batch) Off-peak scheduled job (2:00 AM) deletes expired rows in chunked limits of 5,000 using keyset pagination. Prevents table lock. Reclaims disk space and shrinks B-Tree indices.

Production Nightly Cron Job (Chunked Keyset Deletion)

python • cron_expire_cleaner.py (Runs daily at 02:00 UTC) Non-blocking Batch Loop 
import time
from sqlalchemy import text

BATCH_SIZE = 5000

def purge_expired_urls(db_engine):
    total_purged = 0
    while True:
        query = text('''
            DELETE FROM urls 
            WHERE id IN (
                SELECT id FROM urls 
                WHERE expires_at IS NOT NULL AND expires_at < NOW() 
                LIMIT :batch_size
            )
        ''')
        with db_engine.begin() as conn:
            result = conn.execute(query, {"batch_size": BATCH_SIZE})
            rows_deleted = result.rowcount
            total_purged += rows_deleted
            if rows_deleted < BATCH_SIZE:
                break
        time.sleep(0.1) # Sleep 100ms between batches to unblock user queries!
    print(f"Purged {total_purged} expired URLs.")
💡 HTTP 410 GONE VS HTTP 404 NOT FOUND
When a user clicks an expired link, return HTTP 410 Gone instead of HTTP 404 Not Found. 410 explicitly tells search engine crawlers and browsers that the link intentionally expired and will never return, prompting immediate de-indexing from search engines.
Slide 21 of 24 High-Perf Caching

Bloom Filters: Shielding DB from Malicious Cache Penetration

How a tiny 11.4MB probabilistic bit array stops 99% of invalid redirect requests from crashing PostgreSQL.

The Cache Penetration Vulnerability (DDoS Attack)

Suppose an attacker hammers our service with 100,000 QPS of random, non-existent short URLs (e.g. bit.ly/xxxx999):

  1. Redis Cache MISS: The random slug does not exist in Redis (2ms).
  2. PostgreSQL DB PENETRATION: The request bypasses cache and queries the DB disk B-Tree index (10ms).
  3. Database Overload: 80,000 queries/sec saturate DB connection pools and disk I/O, crashing the primary cluster!

The Bloom Filter Solution: Probabilistic Gatekeeper

A Bloom Filter is a space-efficient bit array that can definitively state:

• "Item is definitely NOT in DB" → 100% Guaranteed!
• "Item MIGHT be in DB" → ≤ 1% False Positive Rate.
  • ✓ For 10,000,000 URLs with 1% false-positive probability ($p=0.01$):
  • ✓ Bits required: $m = -\frac{n \ln p}{(\ln 2)^2} \approx \mathbf{11.4\text{ MB}}$.
  • ✓ Entire bit array lives in L3 CPU cache or Redis cluster via BF.EXISTS!
💡 REDIS MODULE INTEGRATION: RedisBloom
In modern infrastructure, Redis provides native C-speed Bloom Filters via the RedisBloom extension. Commands: BF.RESERVE urls_bf 0.01 10000000, BF.ADD urls_bf "4kycpo", and BF.EXISTS urls_bf "fake_slug" execute in sub-millisecond time.

1. What is a URL Shortener & The 5-Step Interview Framework

A URL shortener converts long, unwieldy destination URLs (often 100+ characters loaded with UTM tracking tokens and search queries) into concise, 6-7 character alphanumeric slugs. For instance:

Input: https://www.facebook.com/anindya.s.dasgupta/ (42 chars)
Output: https://bit.ly/4kycpo (6-char slug: '4kycpo' • 90% reduction)

To successfully execute this problem in a high-stakes engineering interview, you must follow the battle-tested 5-Step System Design Interview Framework:

  1. Functional & Non-Functional Requirements: Clarify core features, read-to-write ratios, SLAs, and capacity boundaries.
  2. Core Entity Identification: Define domain models (User, URL) and relationship cardinality.
  3. REST API Design: Establish clean HTTP endpoints with idempotency, payloads, and response status codes.
  4. High-Level Architecture (HLD): Lay out the basic 4-box architecture (Client, Load Balancer, Application Servers, Database).
  5. Deep Dive & Bottlenecks: Analyze unique ID generation algorithms, distributed caching, database indexing, edge cases, and high-concurrency scaling.

2. Requirements & Rigorous Capacity Estimations

URL shorteners are notoriously read-heavy workloads. When a promotional tweet or marketing campaign goes live, millions of people click the link, while only a small handful of marketers generate new short URLs.

Functional Scope

  • ✓ Generate clean 6-7 character short URLs from valid long URLs.
  • ✓ HTTP redirect incoming short URLs to destination in < 2ms.
  • ✓ Support custom vanity slugs (e.g. bit.ly/summer-sale).
  • ✓ Configurable expiration dates with automatic link retirement.

Non-Functional SLAs

  • ✓ Availability: 99.99% uptime (downtime breaks millions of links).
  • ✓ Latency: p99 redirect < 10ms, p99 write < 100ms.
  • ✓ Uniqueness: 100% collision-free guarantee across billions of URLs.
  • ✓ Unpredictability: Non-guessable IDs to prevent URL enumeration scrapers.

System Sizing Math

  • Write Throughput: 100 Million new URLs created per month → $100\text{M} / (30 \times 86400) \approx 40\text{ URLs/sec}$. Peak load (10x) = 400 writes/sec.
  • Read Throughput (100:1 Read-to-Write): 100 Million $\times 100$ = 10 Billion redirects/month → 4,000 read QPS average, with peak traffic reaching 40,000 to 80,000 QPS.
  • Storage Sizing: Average URL row = 500 bytes (Short code 10B + Destination 400B + Metadata 90B). Over 5 years: $100\text{M} \times 12 \times 5 = 6\text{ Billion URLs} \times 500\text{ bytes} \approx \mathbf{3\text{ Terabytes}}$. Very manageable for PostgreSQL or MySQL!
  • Cache Memory (80-20 Pareto Rule): 20% of daily URLs generate 80% of redirect clicks. Daily read volume = $10\text{B} / 30 \approx 330\text{M clicks/day}$. Caching 20% of daily URLs requires: $66\text{M URLs} \times 500\text{ bytes} \approx \mathbf{33\text{ GB of RAM}}$ in Redis!

3. Core Entities, Relational Schema & REST APIs

The domain requires two core models: User and URL. The relationship is strictly 1-to-Many: One registered user can create millions of short links, but each short link belongs to exactly one user (or null for anonymous links).

4. The Three ID Generation Architectures

How do we generate guaranteed unique, short (6-7 char) strings at high scale? The lecture whiteboard breaks this down into three distinct approaches:

Approach 1: SHA-1 / MD5

Hash destination URL with SHA-1, take first 7 chars. Flaw: Deterministic hashes produce identical outputs for identical URLs, and hash collisions require expensive DB retry loops (= 16ms + 16ms latency penalty).

Approach 2: Redis Counter

A centralized Redis instance issues atomic incremental integers (INCR). Flaw: Single Point of Failure (SPOF) and network bottleneck at > 50,000 writes/sec.

Approach 3: Snowflake (Winner)

Distributed 64-bit integer generator. Servers use local clocks and pre-assigned ZooKeeper worker IDs. Generates 4,096 IDs per millisecond per node with zero network RPCs!

5. Wire Protocols, Caching, and Abuse Protection

Redirecting traffic involves crucial tradeoffs between HTTP 301 and HTTP 302:

  • HTTP 301 (Moved Permanently): The browser caches the redirect mapping permanently. Subsequent clicks bypass your servers entirely, saving bandwidth but destroying click analytics.
  • HTTP 302 (Found / Temporary): The browser queries your servers on every click. Enables 100% click telemetry, geolocation tracking, and instant URL revocation.

To protect your database from DDoS attacks requesting random invalid short codes, install a Redis Bloom Filter in front of the cache. Consuming only 11MB of memory for 10 million URLs, it rejects non-existent keys in sub-millisecond time with a 0% false negative rate!

🎯 The 4 Master Interview Questions & Battle-Tested Answers

MASTER QUESTION 1 Topic: ID Generation & Uniqueness

"How do you generate guaranteed unique short URLs at scale without collisions?"

The Senior Engineer Answer:

"We have three architectural options:

  1. Hash-Based (SHA-1/MD5): Deterministic and deduplicating, but truncation to 7 chars incurs a 0.2% collision rate at 10M URLs, causing expensive DB retry cascades (= 16ms + 16ms).
  2. Centralized Counter (Redis/ZooKeeper): Produces short, clean IDs, but centralized counters create a network bottleneck and Single Point of Failure (SPOF) beyond 50K writes/sec.
  3. Twitter Snowflake (Recommended): A distributed 64-bit ID generator combining a 41-bit timestamp, 10-bit worker ID, and 12-bit local sequence. When boot-strapped with Apache ZooKeeper ephemeral znodes, worker nodes generate 4,096 IDs per millisecond locally with zero network coordination. We then Base62 encode this 64-bit integer into a 7-character URL-safe string ($62^7 = 3.52\text{ Trillion}$ capacity)."

Crucial Interview Edge: Mention that an atomic UNIQUE constraint on urls.short_url in PostgreSQL acts as our final ACID safety net.

MASTER QUESTION 2 Topic: Scalability & Latency SLAs

"How do you handle 1 Billion redirects per day with sub-5ms p99 latency?"

The Senior Engineer Answer:

"1 Billion redirects/day translates to ~11,500 read QPS average and ~80,000 peak QPS. We conquer this using a 4-tier caching and read-scaling topology:

  1. Edge Anycast DNS & CDN Caching: For viral URLs (top 0.1% that generate 50% of traffic), Cloudflare/CloudFront edge nodes terminate connections within 50ms globally.
  2. Dedicated Decryption Tier: 80% of our servers handle reads, entirely isolated from the 20% write encryption tier.
  3. Distributed Redis Cluster (LRU): Following the 80-20 Pareto principle, caching the top 20% of daily URLs requires only 33 GB of RAM. Redis achieves > 90% cache hit rate with sub-2ms response times.
  4. PostgreSQL Read Replicas: The remaining 10% cache misses (~8,000 QPS) are distributed across 5 read-only DB replicas (each handling ~1,600 QPS on an indexed B-Tree seek)."
MASTER QUESTION 3 Topic: Protocols & Analytics Tradeoff

"Should you return HTTP 301 or HTTP 302 for redirects? What is the business impact?"

The Senior Engineer Answer:

"This is a fundamental tradeoff between infrastructure cost and analytics capability:

  • HTTP 301 (Moved Permanently): The browser caches the redirect mapping permanently. Subsequent clicks never touch our servers. While this minimizes server load and yields the fastest end-user redirect, we lose 100% of repeat click analytics, user-agent data, and geolocation tracking! Furthermore, we cannot instantly revoke malicious links or expire dead promotions.
  • HTTP 302 (Found) / 307 (Temporary Redirect): The browser must query our servers on every single click. Although this increases read traffic to 80,000 QPS, it allows us to emit click events to Apache Kafka asynchronously, collect granular telemetry, and immediately enforce link expiration (410 Gone).

Verdict: Pure redirection platforms use 301, but modern marketing shorteners (Bitly, Dub.co) use 302 or 307 because click analytics are the primary monetization driver."

MASTER QUESTION 4 Topic: Security & Abuse Prevention

"How do you stop spammers from weaponizing the URL shortener for phishing and malware?"

The Senior Engineer Answer:

"We implement a defense-in-depth security model across 4 tiers:

  1. Rate Limiting: Redis token-bucket rate limiter restricts anonymous users to 100 URL creations per hour per IP. Authenticated API keys receive 10,000/day.
  2. Async Malware Scanning: On link creation, the destination URL is asynchronously dispatched to Google Safe Browsing API and cross-referenced with PhishTank/URLhaus bloom filters. Flagged URLs are instantly deactivated.
  3. Homograph & Typosquatting Detection: We compute the Levenshtein Edit Distance between the destination domain and top 1,000 high-risk domains (e.g., paypa1.com vs paypal.com). If distance is 1 or 2, we force an Interstitial Warning Screen.
  4. Cache Penetration Shield: A Redis Bloom Filter blocks arbitrary brute-force 404 URL scans from reaching PostgreSQL, protecting disk I/O from exhaustion."

CARD 01 / 08

Why do we use Base62 encoding instead of Base64 or Hexadecimal?

↶ Click to reveal answer
ANSWER 01

Hex (Base16) yields only $16^7 \approx 268\text{M}$ URLs (too small). Base64 includes + and /, which require URL %-encoding. Base62 (0-9, a-z, A-Z) is 100% URL-safe without escaping and yields 3.52 Trillion URLs at 7 characters!

CARD 02 / 08

What is the capacity formula for a 7-character Base62 string?

↶ Click to reveal answer
ANSWER 02

$62^7 = \mathbf{3,521,614,606,208}$ (over 3.52 Trillion URLs). At a generation rate of 100 Million new URLs every month, this single 7-character namespace will last for over 2,900 years without exhausting!

CARD 03 / 08

What is the "= 16ms + 16ms" penalty in Approach 1 (SHA-1 hashing)?

↶ Click to reveal answer
ANSWER 03

When truncating a 160-bit SHA-1 hash to 7 chars, hash collisions occur. The server takes 1ms to hash, 5ms to query DB, detects collision, re-hashes with salt, and queries DB again → 16ms + 16ms cascade that collapses write throughput under high concurrency!

CARD 04 / 08

Why is a single Redis counter a dangerous bottleneck in Approach 2?

↶ Click to reveal answer
ANSWER 04

A single Redis node executing INCR is a Single Point of Failure (SPOF). If it crashes, all URL generation stops. Furthermore, network round-trips (2-3ms) saturate the single thread, capping global write throughput at ~50K QPS.

CARD 05 / 08

How does Apache ZooKeeper coordinate Snowflake worker nodes?

↶ Click to reveal answer
ANSWER 05

Encryption servers register an ephemeral sequential znode (e.g. /app1/p_1 → workerID: 123) at boot time. ZooKeeper guarantees unique worker IDs (0 to 1023). When a server dies, its session expires and frees the ID. Zero runtime RPCs!

CARD 06 / 08

What is the critical business drawback of returning HTTP 301 redirects?

↶ Click to reveal answer
ANSWER 06

Browsers cache HTTP 301 responses indefinitely on disk. Subsequent user clicks bypass the backend shortener entirely. Result: Zero click telemetry, zero user-agent/geo tracking, and no ability to expire or revoke links!

CARD 07 / 08

How does a Bloom filter stop Cache Penetration DDoS attacks?

↶ Click to reveal answer
ANSWER 07

When an attacker queries random non-existent short URLs, they miss Redis. A Bloom filter (11MB for 10M keys) checks the key: if bits are 0, it guarantees 100% the key does not exist and returns HTTP 404 instantly without querying PostgreSQL disk!

CARD 08 / 08

How does Dual-Layer expiration eliminate "Zombie Links"?

↶ Click to reveal answer
ANSWER 08

Layer 1 (Passive): On read access, check expires_at < now() and return 410 Gone. Layer 2 (Batch Cron): A nightly 2:00 AM batch job deletes expired rows in chunks of 5,000 to reclaim disk and B-Tree space without locking the database table.
