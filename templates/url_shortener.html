Slide 02 of 22 Problem Anatomy

Problem Statement: Designing a URL Shortener Like Bitly

A URL shortener accepts an arbitrary long URL and produces an extremely compact 5-to-7 character alias. When a user requests the short alias, the service must reliably redirect them back to the original long destination.

Original Long URL:
https://www.facebook.com/profile.php?id=1000928374659281&ref=bookmarks&source=feed
▼ 1-to-1 Bidirectional Mapping (Shortening Logic) ▼
Compact Short URL:
https://bit.ly/x9R2pM
Domain: bit.ly/ + Token: x9R2pM
FIGURE 2.1: Domain prefix remains constant; only the 6-character unique identifier changes.
🎯 The Core Mechanical Objective

The system acts as a high-speed, distributed dictionary. It must store a bi-directional mapping between short_code and long_url. The domain name (e.g., bit.ly/ or tiny.notes/) never changes—only the token path is generated by our backend.

🔍 The Interviewer's Trap

Interviewers intentionally start with: "Design Bitly." This is deliberately vague! They are waiting to see if you ask clarifying questions about traffic scale, expiration policies, custom aliases, and whether the service needs strict ACID banking-level consistency.

Slide 03 of 22 Step 1: Scoping

Step 1: Gathering Functional Requirements

Functional requirements define the core behaviors of the application. In the lecture, Bunny categorizes these into 2 core mandatory requirements and 2 premium business extensions.

✅ Core Mandatory Requirements
  • 1. URL Shortening: Given any valid HTTP/HTTPS URL, generate and return an ultra-short unique alias of 5 to 7 characters.
  • 2. URL Redirection: When a client requests https://bit.ly/{token}, redirect their browser to the original destination in minimum latency.
⭐ Premium Business Extensions
  • 3. Custom Vanity Aliases: Allow premium users to choose their own custom alias (e.g., bit.ly/ASD or bit.ly/summer-sale).
  • 4. Expiration Date (TTL): Standard links expire after 90 days. Premium users can specify custom expiration dates or permanent links.

Requirement Type Access Level Default Behavior
Shorten Long URL Functional All Users (Public) Auto-generated 6-char token
HTTP Redirection Functional All Users (Public) HTTP 301 / 302 Redirection
Custom Vanity Alias Extension Premium Users Check DB uniqueness; reject if taken
Custom Expiry (TTL) Extension Premium Users Default: 90 days expiration
Slide 04 of 22 Step 1: Quantifying SLAs

Step 1: Non-Functional Requirements & Scale Numbers

Never just write "high availability" or "low latency". As Bunny emphasizes, you MUST quantify every non-functional requirement with concrete numerical targets to guide hardware and database selection.

⚡ Latency Budget
< 200 ms

Explicitly specify where latency applies: both on URL creation AND on redirection. A redirect must complete in sub-200ms.

📈 System Scale
100M DAU

100 Million Daily Active Users generating over 1 Billion long-form URLs. This scale rules out single-server monoliths.

🔒 100% Uniqueness
0 Collisions

Every generated short alias must map to exactly one long URL. No two users must ever receive the same short link.

💡 Why Scale Numbers Change Architectural Decisions

If the interviewer specifies 10,000 URLs total, a simple relational SQLite table with MD5 hashing and a while-loop collision check is sufficient. But for 1 Billion URLs and 100M DAU, DB collision loops will melt your database and spike latency. Scale numbers dictate the design.

Slide 05 of 22 Distributed Systems

The CAP Theorem: Why Availability Trumps Consistency

Since 100M DAU requires a distributed microservice cluster, the CAP Theorem dictates that under network partition, we must choose between Consistency (CP) or Availability (AP).

🏦 When is Strong Consistency (CP) Required?

Banking accounts, payment gateways, and airline seat reservation systems demand strict Read-After-Write Consistency. If Seat 14A is booked at 12:00:00.000, no second user can book it at 12:00:00.001. A delay causes severe business failure.

🌐 Why URL Shorteners Choose High Availability (AP)

If Bitly is down or unreachable, users immediately abandon the service. However, when a user creates a short link, it takes them several seconds to copy and paste it into an email or WhatsApp! We do not need sub-millisecond atomic consistency across all replica nodes.

FIGURE 5.1: Eventual Consistency is acceptable; 200ms propagation delay to replica nodes causes zero user friction.

Bunny's Rule: "We design an eventually consistent, highly available system. The system must never reject traffic or throw a 500 server error."

Slide 06 of 22 Step 2: Data Modeling

Step 2: Identifying the Core System Entities

Because a URL shortener is conceptually lightweight, there are only three core entities involved in the entire lifecycle. Identifying them upfront makes high-level design and schema definition straightforward.

1. Short URL Entity
  • short_code (Unique 6-7 char token)
  • created_at timestamp
  • expires_at timestamp
  • is_custom boolean
2. Long URL Entity
  • original_url (Full destination string)
  • Protocol (http:// or https://)
  • Sanitized target format
  • Payload size up to 2,048 bytes
3. User Metadata Entity
  • user_id (Unique ID)
  • account_tier (Free vs Premium)
  • Created links list
  • Rate limit quota usage
💡 Entity Cardinality

One User can own zero to many Short URLs (1-to-N). Each Short URL maps to exactly one Long URL (1-to-1). Multiple users can shorten the same destination, but each gets their own unique short alias if analytics isolation is desired.

Slide 07 of 22 Step 3: Interface Contracts

Step 3: Defining the REST API Endpoints

With functional requirements and entities defined, API design is a direct 1-to-1 mapping. We need exactly two primary REST endpoints: one to create short links, and one to resolve them.

POST /api/v1/urls Create Short URL 
POST /api/v1/urls HTTP/1.1
Host: bit.ly
Content-Type: application/json

{
  "long_url": "https://facebook.com/profile...",
  "custom_alias": "ASD",       // Optional (Premium)
  "expires_at": "2026-12-31"   // Optional (Premium)
}

// Response (HTTP 201 Created):
{
  "short_url": "https://bit.ly/ASD",
  "long_url": "https://facebook.com/profile...",
  "created_at": "2026-10-19T10:00:00Z",
  "expires_at": "2026-12-31T23:59:59Z"
}
GET /{short_url} Redirect Handler 
GET /ASD HTTP/1.1
Host: bit.ly
User-Agent: Mozilla/5.0...

// Response (HTTP 301 / 302 Redirect):
HTTP/1.1 302 Found
Location: https://facebook.com/profile...
Cache-Control: no-cache, no-store
Date: Mon, 19 Oct 2026 10:00:01 GMT

REST Design Rule: The redirect endpoint does not return a JSON body to browser clients; it returns an HTTP status code 301 Moved Permanently or 302 Found with the Location header set to the destination URL.

Slide 08 of 22 Step 4: Architecture Blocks

Step 4: High-Level Design (HLD) Architecture

Before getting bogged down in low-level libraries, we draw the abstract 30,000-foot component flow: Client, Backend Server, and Database, mapping out both read and write request cycles.

FIGURE 8.1: High-Level Design abstract data flow for URL creation and resolution.
📝 Write Path (URL Shortening)

1. Client calls POST /api/v1/urls with long_url.
2. Backend server generates a unique short token.
3. Server saves (short_url, long_url) mapping in database.
4. Returns compact short URL back to client.

⚡ Read Path (URL Redirection)

1. Client enters bit.ly/token in browser address bar.
2. Backend server queries database for matching short_url.
3. If found, returns HTTP 301/302 with Location: long_url.
4. Browser automatically navigates user to the destination.

Slide 09 of 22 Schema Architecture

Database Schema Design & Indexing Strategy

We do not need a complex schema with 20 tables. We need exactly two relational tables: users and urls, with a mandatory B-Tree Unique Index on `short_url`.

TABLE: urls Critical Mapping 
CREATE TABLE urls (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  short_url VARCHAR(7) NOT NULL,
  long_url VARCHAR(2048) NOT NULL,
  user_id BIGINT,
  custom_url VARCHAR(255),
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  expires_at TIMESTAMP NULL,
  
  -- MANDATORY PRIMARY LOOKUP INDEX
  CONSTRAINT uq_short_url UNIQUE (short_url)
);

CREATE INDEX idx_user_id ON urls(user_id);
TABLE: users Metadata & Tier 
CREATE TABLE users (
  user_id BIGINT PRIMARY KEY AUTO_INCREMENT,
  email VARCHAR(255) UNIQUE NOT NULL,
  is_premium BOOLEAN DEFAULT FALSE,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- Why PostgreSQL / MySQL?
-- 1. Simple key-value mapping structure
-- 2. Strict unique constraints on short_url
-- 3. Mature B-Tree indexing for O(log N) lookups

Crucial Indexing Rule: Every incoming redirect issues SELECT long_url FROM urls WHERE short_url = ?. Without a B-Tree index on short_url, the database must perform a full-table scan across 1 Billion rows, causing a query timeout!

Slide 10 of 22 Step 5: The Core Meat

Step 5: Low-Level Design & The 3-Approach Evolution

This is where 90% of candidates fail or win the interview. How does the server actually generate a 6-character short URL without collisions at 1 Billion scale? We analyze the 3 classic approaches in order.

❌ Approach 1

MD5 / SHA-1 Hashing

Hash long_url with MD5/SHA-1, crop the first 6 characters, and loop query the DB to resolve collisions.

FAILS: Collision Cascades at Scale
⚠️ Approach 2

Counter / Distributed Redis

Increment an integer counter (1, 2, 3...). In microservices, local counters collide; a single Redis counter becomes a SPOF.

FAILS: Single Point of Failure (SPOF)
✅ Approach 3 (Hybrid)

ZooKeeper + Snowflake

ZooKeeper registers workers on boot only. Each server creates 64-bit Snowflake IDs in-memory with zero network calls!

OPTIMAL: 100% Unique & Bulletproof

Bunny's Pedagogical Strategy: "Start with Approach 1, explain its exact latency numbers and failure points. Transition to Approach 2 to show scaling awareness. Then deliver the Hybrid ZooKeeper solution to guarantee an offer."

Slide 11 of 22 Approach 1: Hashing

Approach 1: MD5/SHA-1 Hashing & The Truncation Flaw

The first instinct of most developers is to pass the long URL into an established hashing library like MD5 (128-bit) or SHA-1 (160-bit) and take the first 6 characters. Let's see why this breaks.

1. Input: https://facebook.com/user1 ──▶ MD5: 9191c0a4b7f8e3d2... (32 hex characters)
2. Input: https://amazon.com/product99 ──▶ MD5: 9191c088ef3a1b4c... (32 hex characters)
⚡ Truncate to first 6 chars: Both become "9191c0"! ──▶ COLLISION COLLAPSE!
FIGURE 11.1: Truncating a 32-character hash to 6 characters destroys uniqueness guarantees.
⚠️ The Mathematical Dilemma

MD5 outputs a 32-character hexadecimal string. SHA-1 outputs 40 characters. If you return all 32 characters, the URL is not "shortened"—it defeats the user requirement! But if you crop it to 6 characters, you run head-first into the Birthday Paradox.

💥 Similar URLs Produce Identical Prefixes

When shortening millions of URLs with similar query parameters or paths, there is a non-trivial probability that two distinct URLs share the exact same first 6 characters, causing immediate primary key collision in the database.

Slide 12 of 22 Latency Breakdown

Approach 1 Failure: The Collision Retry Cascade

To resolve collisions in Approach 1, the system must check the database before returning the key. In the lecture, Bunny breaks down the exact millisecond latency cost of this retry loop.

FIGURE 12.1: DB lookup latency compounds linearly with every collision retry.
💣 What Happens at 1 Billion URLs?

As the database fills with hundreds of millions of rows, the chance of hitting an existing 6-character token escalates exponentially. A user request may suffer 5 to 10 collision loops, pushing latency past 150ms–200ms, directly violating our SLA!

📊 Final Verdict on Approach 1

Where it works: Small internal tools with < 100,000 URLs.
Where it fails: Production internet-scale systems. We cannot rely on blind hash truncation paired with blocking database collision scans.

Slide 13 of 22 Approach 2: Counters

Approach 2: Counter-Based Generation & Monolith Scaling Wall

Instead of hashing unpredictable text strings, what if the server uses an auto-incrementing counter (1, 2, 3, 4...)? Each request gets a unique integer, dropping DB collision scans completely!

⚡ Why Counters Slash Latency to 6ms

Request 1 receives ID 1. Request 2 receives ID 2. Because numbers strictly increment, duplicates are mathematically impossible! We no longer need to execute a 10ms database scan. Latency drops from 16ms to just 6ms (local increment + DB save).

🧱 The Monolith Scaling Wall

This single counter works flawlessly on a single monolithic server. But our non-functional requirement specifies 100 Million DAU! A single machine cannot handle this throughput. We must scale horizontally with microservices.

Vertical Scaling (Bigger RAM/CPU) ❌ DOES NOT SCALE TO 100M USERS
▼ MUST USE HORIZONTAL MICROSERVICE REPLICATION ▼
Horizontal Scaling (Multiple App Servers behind Load Balancer)
Slide 14 of 22 Concurrency Failure

Approach 2 Flaw: Load Balancers & Local Counter Collisions

When we deploy multiple server instances (Server 1, Server 2, Server 3) behind a Round-Robin Load Balancer, a catastrophic concurrency bug appears: each server maintains its own local counter.

FIGURE 14.1: When servers boot independently, their counters start at 0 and overwrite each other's keys.

The Failure: Server 1 gets request 1 and returns 0. Server 2 gets request 2 and also returns 0! The database crashes with a duplicate key violation. Local counters cannot exist in distributed systems.

Slide 15 of 22 Centralized Cache

Approach 2.5: Centralized Redis Counter & SPOF Risk

To fix local counter collisions, developers introduce a central Redis cache. Because Redis is single-threaded, INCR counter provides atomic increments in 2–3ms. But this creates a dangerous Single Point of Failure.

✅ The Redis Counter Advantage

All app servers consult one central Redis instance via atomic INCR url_counter. No local counters collide. Latency is only 2ms to 3ms. For medium-scale systems, this solves the collision problem.

💥 Single Point of Failure (SPOF)

If the Redis instance crashes or experiences network isolation, the entire URL shortening service halts! If you deploy a multi-node Redis Cluster, synchronizing distributed counters across nodes recreates the exact split-brain duplicate problem we tried to avoid.

🚨 THE ARCHITECTURAL DILEMMA:
Single Redis Node ──▶ Single Point of Failure (SPOF)
Multi-node Redis Cluster ──▶ Cross-node counter synchronization race conditions & duplicates!
How can we generate unique IDs locally with ZERO external network calls?
Slide 16 of 22 Distributed Coordination

Understanding Apache ZooKeeper: The Cluster Coordinator

Before presenting the final hybrid solution, Bunny explains what Apache ZooKeeper actually is: a centralized, highly reliable coordination service that monitors distributed worker nodes like a parent.

🌲 Hierarchical ZNode Directory Tree

ZooKeeper stores configuration like a computer's directory tree. The root node has sub-folders for each registered service (e.g. /url-shortener/worker-1). Nodes store configuration metadata and state in memory.

💓 Persistent vs Ephemeral Nodes

Persistent Nodes: Never deleted automatically. Perfect for cluster counters and configuration.
Ephemeral Nodes: Tied to server heartbeat. If an app server crashes, ZooKeeper drops its ephemeral znode instantly.

FIGURE 16.1: ZooKeeper's hierarchical tree structure managing persistent state and ephemeral heartbeats.
Slide 17 of 22 The Optimal Architecture

Approach 3: The Hybrid ZooKeeper Solution

Here is Bunny's bulletproof breakthrough: We do NOT call ZooKeeper on every request! We only consult ZooKeeper once when a server boots up to assign it a unique worker_id.

🚀 ZooKeeper Called ONCE on Boot Only

When Server 1 launches, it registers with ZooKeeper and receives worker_id = 123. Server 2 receives worker_id = 234. Server 3 receives worker_id = 345. During active runtime, zero network calls are made to ZooKeeper!

🛡️ What If ZooKeeper Crashes?

Even if ZooKeeper goes completely offline, all running application servers continue generating unique URLs smoothly without interruption! ZooKeeper is only needed when new server instances boot or scale up.

FIGURE 17.1: ZooKeeper isolates coordination to boot-time worker allocation, removing runtime SPOF bottlenecks.
Slide 18 of 22 Distributed ID Generation

The 64-Bit Snowflake ID Architecture

With a unique worker_id assigned by ZooKeeper, each server generates a 64-bit Snowflake ID entirely in-memory. Because time, machine ID, and local sequence counter are combined, uniqueness is 100% mathematically guaranteed.

FIGURE 18.1: Complete 64-bit binary layout of the Twitter Snowflake ID format.
41-Bit Timestamp

241 milliseconds ≈ 69.7 years of unique, roughly time-sorted keys.

10-Bit Worker ID

210 = 1,024 independent server instances can run concurrently without collision.

12-Bit Local Sequence

212 = 4,096 unique IDs per millisecond on a single worker node!

The Breakthrough: Generating a Snowflake ID requires 0ms network round-trip time. It is computed in CPU registers in less than 1 microsecond!

Slide 19 of 22 Encoding Pipeline

The Hybrid Encoding Step: Converting Snowflake to 6 Characters

Now that we have a 64-bit integer guaranteed 100% unique across all servers and time, how do we convert it into a short 6-to-7 character string? We pass our Snowflake ID into Base62 or MD5.

🔠 Why Base62 is Superior

Base62 consists of [0-9, a-z, A-Z] (10 digits + 26 lowercase + 26 uppercase = 62 characters).
• 6 characters: 626 = 56.8 Billion URLs
• 7 characters: 627 = 3.52 Trillion URLs
Converting a 64-bit integer to Base62 is a simple mathematical change of base: ID % 62 with zero hash collisions possible!

🛡️ Why Hashing Snowflake Works (Unlike Approach 1)

In Approach 1, hashing long URLs produced collisions because different URLs had similar text prefixes. But here, the input key to MD5 is our Snowflake ID. Because the input spectrum is guaranteed 100% globally unique, the cropped hash has an almost zero probability of collision!

Unique Snowflake ID: 154829104829104829
  ──▶ Base62 Conversion [ID % 62] ──▶ b9X7qL (6 chars)
  ──▶ Prepend Domain ──▶ https://bit.ly/b9X7qL
FIGURE 19.1: The complete hybrid generation pipeline yielding zero collisions and microsecond latency.
Slide 20 of 22 Production Edge Cases

Handling Custom Aliases & Dual-Layer Expiration

In production, two functional requirements require special architectural handling: Custom Vanity Aliases for premium users, and Dual-Layer Expiration (Cron Job + Redis TTL).

✨ Custom Vanity Alias Flow

When a premium customer requests bit.ly/ASD, we bypass the Snowflake generator! The backend directly executes: SELECT 1 FROM urls WHERE short_url = 'ASD'; If found, return HTTP 409 Conflict (Alias Taken). If free, insert into database and reserve immediately.

⏱️ The Zombie Hot-Key Danger

A daily database Cron Job runs at midnight deleting expired rows (DELETE FROM urls WHERE expires_at < NOW()).
The Trap: If a hot link is in Redis cache, deleting it from the DB does NOT evict it from Redis! You MUST set an explicit Redis TTL matching the expiration date, otherwise expired links stay alive indefinitely in memory!

FIGURE 20.1: Dual-layer synchronization prevents expired hot keys from remaining zombie-accessible in Redis.
Slide 21 of 22 Protocol Mechanics

Redirection Mechanics: HTTP 301 vs HTTP 302

When returning the redirect to the client, should you use HTTP 301 Moved Permanently or HTTP 302 Found? Bunny explains that this architectural decision directly impacts server bandwidth versus analytics tracking.

301 Moved Permanently
  • Browser Action: Browser permanently caches the mapping in local disk cache.
  • Subsequent Clicks: Never hit our server again! Browser redirects locally.
  • PRO: Drastically reduces server traffic, bandwidth cost, and latency.
  • CON: Destroys click analytics! You cannot track total clicks, country, or user agent.
302 Found (Temporary)
  • Browser Action: Browser executes redirect immediately without caching locally.
  • Subsequent Clicks: Every single click hits our backend.
  • PRO: 100% accurate click tracking! Enables telemetry dashboards, advertising, and AI/ML pipelines.
  • CON: Higher request volume hitting our load balancers and cache.

Senior Engineer Decision Matrix: If your business model charges premium customers for click analytics dashboards (like Bitly Enterprise), you MUST choose HTTP 302. If your goal is purely offloading bandwidth for internal tools, choose HTTP 301.
