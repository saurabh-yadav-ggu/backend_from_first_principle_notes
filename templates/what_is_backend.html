What is a Backend? Beyond the Abstract Definition

In its traditional definition, a backend is simply a computer listening for HTTP, WebSocket, gRPC, or other network requests through open ports (like Port 80 or 443) accessible over the Internet.

Why do we call it a "Server"?

Because it literally provides or serves content to remote clients! It serves static assets (HTML, CSS, JavaScript, images) or serialized structured data (JSON payloads), and accepts data mutations sent by clients.

The browser looks at the domain backend-demo.senus.xyz. Browsers cannot route packets to domain names; they require an IP (Internet Protocol) address.

Maps a domain or subdomain directly to an IPv4 address of a physical or virtual machine.

Maps an alias domain or subdomain to another domain name rather than directly to an IP address.

Slide 05 of 14 Hop 3: Cloud Infrastructure Security

Hop 3: AWS Security Group & Perimeter Firewall

Once the request packet reaches AWS with the target EC2 IP, it hits the AWS Native Firewall (Security Group) before touching the virtual server's operating system!

The Silent Drop Rule

If incoming traffic requests a port that has not been explicitly allowed in the Security Group inbound rules, AWS drops the packet silently at the edge. The request will time out in the user's browser, and the server never even knows someone tried to connect!

Slide 06 of 14 Hop 4: Web Servers & Reverse Proxies

Hop 4: Nginx Reverse Proxy & SSL Offloading

Inside the EC2 instance, requests are received by Nginx. What is a reverse proxy? It is a specialized server that sits in front of other application servers to handle SSL, redirects, and routing from a centralized location.

1. Automated SSL via Certbot

Certbot automatically provisions Let's Encrypt certificates. Nginx listens on Port 80 (HTTP) and seamlessly redirects clients to Port 443 (HTTPS).

2. Server Name Routing

Based on the incoming HTTP host header (server_name), Nginx decides which internal local port to forward traffic to!

# /etc/nginx/sites-available/default server { server_name backend-demo.senus.xyz; listen 443 ssl; # Managed by Certbot location / { proxy_pass http://localhost:3001; # Internal Node Server proxy_http_version 1.1; proxy_set_header Upgrade $http_upgrade; proxy_set_header Connection 'upgrade'; proxy_set_header Host $host; proxy_cache_bypass $http_upgrade; } }

Slide 08 of 14 Core Principles

Why Do We Need Backends? The Single Word: DATA

If you strip away all frameworks, libraries, protocols, and jargon, the entire existence of backends condenses down to a single word: DATA.

📥
RECEIVE DATA

Accepting client inputs, mutations, uploads, and commands securely.

💾
PERSIST DATA

Saving state into relational tables, document stores, or caches permanently.

📤
FETCH & SERVE

Querying, filtering, sorting, and delivering personalized payloads back to clients.

Centralized Truth

Your client application only knows about you. It has your preferences and cached profile. But to interact with anyone else, there must exist a centralized computer with the complete holistic state of all users.

Slide 10 of 14 Frontend vs Backend Runtime

How Frontends Work: The Browser is the Runtime

The instructor demonstrates a Next.js application deployed on the same EC2 instance under frontend-demo.senus.xyz to illuminate the fundamental difference between frontends and backends.

🖥️ The Frontend Model
  • Server sends down HTML, CSS, and JS files.
  • CSS paints colors, fonts, and layout.
  • JS hydrates event listeners in the client engine.
  • Execution happens inside the client's browser!
⚙️ The Backend Model
  • Client sends request data over TCP socket.
  • Server executes logic on powerful server CPU.
  • Server communicates with database and file system.
  • Processing happens entirely on remote server hardware!
The Natural Question:

"If frontend devices are also computers, why not just connect to the database directly from the browser and avoid backend servers entirely?"

Slide 11 of 14 Why Not Frontend? Part 1

Deal-Breakers 1 & 2: Sandbox Isolation & CORS

Four fundamental technical barriers prevent frontend code from ever functioning as a backend. Here are the first two:

1. Browser Sandbox Isolation

Browsers are strictly isolated sandbox environments. They block JavaScript from touching the local file system or reading OS environment variables. Imagine visiting an unknown website: if browsers weren't sandboxed, that site's JS could read all your private files and bank credentials! Backends require full OS file access for logs, secrets, and caches.

2. CORS Policy Barriers

Cross-Origin Resource Sharing restricts frontend JavaScript to only calling APIs within the same origin domain unless external servers explicitly provide permissive Access-Control-Allow-Origin headers. A backend must freely query 10 different internal microservices without browser security interference.

Slide 12 of 14 Why Not Frontend? Part 2

Deal-Breaker 3: Native DB Drivers & Connection Pools

Databases like PostgreSQL and MongoDB do not communicate via simple HTTP; they require binary TCP socket drivers.

The Connection Pool Secret:

Creating and tearing down database TCP connections takes massive CPU overhead. Backend servers maintain a steady pool of 10 to 50 persistent connections, reusing them continuously to serve hundreds of thousands of queries effortlessly!

Slide 13 of 14 Why Not Frontend? Part 3

Deal-Breaker 4: Client Compute Heterogeneity

Client devices exist everywhere: from an M3 Max MacBook with 64GB RAM to a budget smartphone with 256MB RAM and a single-core CPU running on 2G network connectivity.

📱 The Client Hardware Trap

If heavy business logic, data crunching, sorting, or cryptography ran in the client, low-end devices would lag, overheat, drop frames, and crash. You cannot upgrade your users' phones.

☁️ The Elastic Server Superpower

A centralized backend server can be upgraded in seconds! Need 64 cores and 256GB RAM to crunch data? Spin up a bigger AWS instance or add horizontal replicas behind a load balancer.

Chapter 01 Complete Engineering Handbook

What is a Backend & How Does it Work Behind the Scenes?

A complete, verbatim transcript analysis and architectural handbook covering the physical and logical lifecycle of an HTTP request.

1. The Traditional Definition vs Physical Reality

In its traditional definition, a backend is simply a computer that is continuously listening for HTTP, WebSocket, gRPC, or other network requests through open ports (such as Port 80 for HTTP or Port 443 for HTTPS) that are accessible over the public Internet.

We call this computer a "server" for one straightforward reason: it provides or serves content. This content can be static files (HTML documents, CSS style sheets, JavaScript bundles, client images, custom fonts) or structured serialized data (JSON objects). Furthermore, the server accepts incoming data sent by clients and modifies persistent records accordingly.

The Physical Perspective:

Software engineers frequently treat "the cloud" or "the backend" as a mystical abstraction. But behind every URL you type is a piece of silicon, copper, optical glass, and operating system kernel running software that responds to incoming binary socket buffers.

2. Tracing the 6-Hop End-to-End Request Journey

To demonstrate this with production fidelity, the instructor sets up an AWS EC2 instance running a live backend at https://backend-demo.senus.xyz/users. When a user navigates to this URL in a web browser, trace the exact hops the packet takes:

Hop 1: The Browser Request Socket

The browser takes the target URL and creates an HTTP/1.1 or HTTP/2 GET request. Before sending data, it inspects the host string backend-demo.senus.xyz. Because internet routers operate strictly on IP addresses rather than human-readable domain names, the browser immediately queries the Domain Name System.

Hop 2: Authoritative DNS Resolution

The DNS server inspects its configured zone records:

  • A-Records (Address Records): Point a domain or subdomain directly to an IPv4 address. Here, backend-demo has an A-record pointing to the public IP of the AWS EC2 instance.
  • CNAME Records (Canonical Name): Point a domain to another domain or subdomain rather than directly to an IP.

With the IP in hand, the browser initiates a TCP 3-way handshake (SYN → SYN-ACK → ACK) and TLS negotiation over Port 443 directly with that IP.

Hop 3: The AWS Security Group Firewall

Before the network packet can reach the EC2 instance's virtualized network card, it must pass through the AWS Native Firewall (Security Group). The Security Group enforces inbound traffic rules:

Inbound Rules: - Port 22 (SSH) → Allowed for remote administrative console logins. - Port 80 (HTTP) → Allowed for standard unencrypted web traffic. - Port 443 (HTTPS) → Allowed for encrypted TLS traffic. - Port 3000/3001 → NOT allowed from the Internet (Silently dropped).

If a client attempts to connect to Port 3001 directly from the internet, the AWS firewall drops the packet silently at the edge. The server OS never sees the connection.

Hop 4: Nginx Reverse Proxy & SSL Offloading

Traffic arrives on Port 443 at the EC2 instance where Nginx is listening. Nginx serves as a reverse proxy: a server that sits in front of other backend application servers to handle SSL certificates, redirects, and routing.

Certbot automatically assigns Let's Encrypt SSL certificates. If a request arrives on Port 80, Nginx redirects it to Port 443. Nginx then inspects the server_name header. Because the host is backend-demo.senus.xyz, Nginx forwards the traffic internally to http://localhost:3001.

Hop 5: PM2 Process Management & Node Server

On the local loopback interface, a Node.js server is listening on Port 3001. It is managed by PM2 (a production process manager that restarts crashed servers and handles background daemons). The Node server parses the route /users, runs application business logic, and queries persistent storage.

Hop 6: Database Connection Pooling & Return Trip

The Node server queries PostgreSQL or MongoDB via a persistent connection pool, serializes the response records into a JSON string, and sends the HTTP response back through Nginx, out through the AWS firewall, across the internet backbone, and into the client browser!

3. Why Do We Need Backends? (The Power of Centralized Data)

The instructor poses a crucial question: "Why can't everything just happen on the client?"

Consider the Instagram Like Flow: User A likes a photo posted by User B.

  1. User A taps the Heart icon in their mobile app.
  2. The mobile app dispatches an authenticated HTTP POST request to the backend.
  3. The backend authenticates User A's token, verifies the post ID, and writes a persistent like record to the database.
  4. The backend identifies User B as the post author, verifies their notification settings, and pushes a real-time notification to User B's device.
  5. User B's phone displays the push notification.

Your client device is tailored only to your profile. It knows nothing about other users. Without a centralized backend holding global state and mediating interactions, multi-user applications cannot exist.

4. Why Can't We Run Backend Logic on Frontends?

The instructor identifies four absolute architectural deal-breakers:

1. Security Sandboxing: Browsers isolate code from the local operating system to prevent malicious websites from stealing files or hijacking processes. Backends need full OS access for logs, environment secrets (process.env), and configuration vaults.
2. CORS Restrictions: The browser blocks cross-domain network calls unless remote servers return explicit permissive CORS headers. Backend servers have raw socket freedom to query any microservice or third-party API without browser barriers.
3. Native Database Drivers & Connection Pooling: Databases communicate via binary TCP sockets, not HTTP. Direct client connections would spawn millions of concurrent sockets, causing immediate database server collapse. Backends maintain efficient pools of 10-50 connections.
4. Compute Power Heterogeneity: Clients run on everything from $20 low-spec phones (256MB RAM) to desktop rigs. Centralized backends guarantee consistent CPU and memory, scaling elastically on demand.

DNS Record Types

A-Record (Address):

Maps a hostname directly to an IPv4 address. Used when pointing backend-demo.senus.xyz to the public IP of an AWS EC2 instance.

CNAME (Canonical Name):

Maps a hostname to another hostname / FQDN. Used when pointing subdomains to AWS Application Load Balancers, Cloudflare, or CDN distributions.

Nginx Reverse Proxy Roles

  • Port 80 → 443 Redirect: Enforces HTTPS transport security across all incoming connections automatically.
  • SSL Offloading: Decrypts TLS packets before proxying plain HTTP over internal loopback (localhost:3001).
  • Virtual Host Routing: Inspects HTTP Host headers to route traffic to multiple apps on one machine.
  • Security Shield: Prevents direct internet exposure to internal application ports (3000, 3001).

The 4 Deal-Breakers Recap

  1. Sandbox: Browsers isolate code; cannot access file systems or secrets.
  2. CORS: Enforces cross-origin boundary policies on external fetches.
  3. DB Pooling: Binary socket drivers require server-side connection pools.
  4. Compute: Cloud servers scale elastically; client devices are heterogeneous.
