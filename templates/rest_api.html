Slide 02 of 25 The Core Problem

The API Design Dilemma: Why Engineers Still Get Confused

Despite decades of research, widespread RFC standards, and extensive collective backend engineering experience, developers in both early and intermediate phases frequently struggle with fundamental API decisions.

🤔 Recurring Architectural Dilemmas

  • Plural vs. Singular URI Segments: Should an endpoint fetching a single book be /book/:id or /books/:id?
  • PUT vs. PATCH for Updates: When updating partial resource attributes, which verb conveys true semantic intent without side effects?
  • Non-CRUD Custom Actions: When executing operations like sending an email, archiving an organization, or cloning a project, which method should be chosen?
  • Status Code Ambiguity: When should 200 vs 201 vs 204 be used? Should an empty list return 404 Not Found or 200 OK?

🔄 The Historical Shift: MPAs to SPAs

The root of this persistent confusion lies in a fundamental historical mismatch between the era when HTTP standards were drafted and the modern web runtime:

Past Era (Multi-Page Apps - MPAs): The web primarily served HTML documents. Form submissions sent complete page states via POST or PUT. Server-side rendering handled state transitions.

Modern Era (Single-Page Apps - SPAs): The initial request downloads all client JavaScript. The client executes routing via browser history and makes asynchronous, fine-grained JSON API calls. Clients heavily prefer partial updates (PATCH).

Slide 05 of 25 Architectural Constraints

The Uniform Interface: 4 Foundational Subconstraints

The Uniform Interface is the defining signature of REST. It simplifies the overall system architecture by establishing a single, uniform way for all distributed components to communicate.

Figure 4.1: The 4 Pillars upholding REST's Uniform Interface constraint.

Pillars 1 & 2: Identification & Manipulation

The URI identifies the conceptual entity; whether it is delivered as JSON or XML is a matter of representation. When a client holds a representation with metadata, it possesses sufficient information to modify or delete the resource on the server.

Pillars 3 & 4: Self-Descriptive & HATEOAS

Each message contains all metadata necessary to interpret it (no secret out-of-band communication needed). Clients transition state by discovering links returned inside server responses.

Slide 07 of 25 Core REST Theory

Deconstructing "REST": Representational State Transfer

What do the three words in Representational State Transfer actually mean when broken down into backend engineering reality?

R Representational

Resources (data models or entities) are represented in specific formats depending on client needs:

  • JSON: Dominant format for API and server-to-server communication.
  • HTML: Visual document representation for web browsers.
  • XML: Legacy structured enterprise format.
S State

Refers to the current condition, properties, or attributes of a resource at a given point in time:

Real-World Example (Amazon Cart):
A Shopping Cart's state includes item IDs, quantities, discount coupons, and calculated total price.
T Transfer

The physical movement of resource representations between client and server over a shared transport protocol:

  • Executed via HTTP verbs (GET, POST, PATCH, DELETE, etc.).
  • When you perform a GET request, you are transferring a representation of the resource from server to client.
Slide 08 of 25 URL Architecture

URL Anatomy & Production Route Architecture

Before designing individual endpoints, backend engineers must master the standard anatomical segments of a Uniform Resource Locator.

PRODUCTION API URL BREAKDOWN
https:// api. example.com /v1 /books /harry-potter ?fields=summary #reviews

🌐 URL Anatomical Segments

  • Scheme: https:// for production encrypted transport; http:// for local dev.
  • Subdomain: Standard industry convention is api.domain.com to decouple API routing from static asset hosting.
  • Versioning: Explicit path versioning (/v1, /v2) protects legacy mobile and third-party consumers from breaking contract changes.
  • Path Segment: Hierarchical resource identifier separated by forward slashes (/).
  • Query Parameters: ?key=value used in GET calls for filtering, pagination, and sorting.
  • Fragment: #section handled purely client-side by browsers; never sent to the server.

🗂️ The Forward Slash (/) Represents Hierarchy

The forward slash represents a strict hierarchical relationship between parent and child resources:

Hierarchical Resource URI Example
/organizations/5/projects/12/tasks

Slide 11 of 25 HTTP Semantics

The Complete HTTP Methods & Idempotency Truth Table

Let us rigorously analyze the 5 primary data methods (and 2 auxiliary methods) according to the official REST specification.

Method Primary Semantic Purpose Idempotent? Safe (Read-Only)? Standard Server Side-Effect
GET Retrieve/fetch resource representation YES YES Zero state mutation on the server.
PATCH Partial resource update (specific fields) YES NO Overwrites specified fields with payload value. Repeated calls set identical values.
PUT Full replacement of resource representation YES NO Completely overwrites entire entity with payload. Repeated calls result in same state.
DELETE Remove specified resource instance YES NO Call 1 deletes record; Call 2 finds nothing. Server state remains: entity is deleted.
POST Create new resource or trigger custom action NO NO Inserts new database record with unique generated ID each call (or triggers action).
HEAD Retrieve headers only (identical to GET) YES YES Zero side effects; used for checking file sizes / timestamps.
OPTIONS Inspect permitted HTTP methods / CORS preflight YES YES Zero side effects; informs client of allowed origin and headers.
Slide 12 of 25 HTTP Semantics

The PUT vs. PATCH Debate in Modern Backend Engineering

Why do frontend and backend developers constantly argue over PUT and PATCH? Let us resolve the semantic distinction once and for all.

Interactive Diff: What happens when client sends {"status": "active"}? Live Semantic Comparison

PATCH: Partial Resource Mutation

The server updates only the specified fields, leaving name, description, and timestamps intact. This matches modern SPA UX where users edit individual form fields.

PUT: Complete Entity Replacement

The client submits a complete representation. If the client omits description, a strict REST server will overwrite the description with null.

Slide 13 of 25 HTTP Semantics

The DELETE Paradox & Why POST is Non-Idempotent

Let us address two of the most common interview traps and conceptual sticking points in HTTP REST semantics.

🗑️ The DELETE Paradox: Why is DELETE Idempotent?

Consider deleting User ID 1:

Request 1: User exists. Server deletes User 1 and responds with 204 No Content.
Request 2: User is gone. Server checks database and responds with 404 Not Found.

Because the state of the server did not change in Request 2, DELETE is 100% idempotent. In Call 1, the user became deleted. In Call 2, the user remains deleted. Zero additional side effects occurred.

➕ Why POST is Strictly Non-Idempotent

Consider creating a Book record with payload {"title": "Harry Potter"}:

Request 1: Server generates ID 101 and inserts record.
Request 2: Server generates ID 102 and inserts another record.
Request 1,000: Server now holds 1,000 distinct book records.

Because primary keys are generated at the database level, repeated identical POST requests create cumulative side-effects. Hence, POST is non-idempotent.

Filtering & The Cardinal Rule: Never 404 an Empty List!

Filtering allows clients to filter collections by state or name attributes. However, handling empty results correctly is one of the most vital rules in REST design.

🚨
The Golden Rule: When a list query or filter yields zero matching records, NEVER return HTTP 404 Not Found! Always return HTTP 200 OK with an empty array.

✅ Correct Empty Collection Response (HTTP 200)

GET /organizations?status=archived
{
  "data": [],
  "total": 0,
  "page": 1,
  "totalPages": 0
}

The Logic: The list endpoint exists, the server processed the query successfully, and the search returned 0 items. An empty set is a completely valid answer.

❌ When is 404 Not Found Actually Appropriate?

HTTP 404 is reserved exclusively for situations where the client requests a specific identified resource that does not exist:

GET /organizations/99999
Status: 404 Not Found
{ "message": "organization not found" }

Slide 23 of 25 Design Standards

The Law of Consistency: Eliminating Consumer Guesswork

The single most important hallmark of an elite backend engineer is predictable consistency across all endpoints and data models.

1. CamelCase for JSON

All JSON keys in request payloads and response bodies must adhere to camelCase:

✅ organizationId
✅ createdAt
❌ organization_id
2. Cross-Resource Matching

If Organization has a description field, Project must use description, NEVER desc or details.

Frontend engineers infer schemas from previously integrated endpoints. Inconsistent naming causes silent bugs.
3. Zero Guesswork

When 80%+ of an API adheres to established standards, frontend integration time plummets and integration meetings disappear.

🚫
The Danger of Abbreviations: Never abbreviate property names (e.g. orgId for organizationId, qty for quantity). The backend engineer possesses complete context that external integration partners do not have. Explicit names prevent catastrophic assumptions.
Slide 24 of 25 Design Standards

The 4 Cardinal Rules for World-Class REST API Design

These four overarching principles summarize the core engineering philosophy taught in this masterclass.

Rule 1: Interactive Documentation from Day 1

Always integrate OpenAPI (Swagger) from the initial planning phase. An interactive playground serves a dual purpose: it acts as your personal test bench during development and serves as the living source-of-truth contract for frontend consumers.

Rule 2: Intuitive & Consistent Route Shapes

Maintain identical patterns for plural resource naming, dynamic parameters, custom actions, and JSON casings across every single resource (Organizations, Projects, Tasks).

Rule 3: Provide Sane Defaults Everywhere

Accept minimal required input. If an organization is created without an explicit status, default to active. If a list call lacks pagination, default to page=1 and limit=10. Never fail a request for missing obvious defaults.

Rule 4: Strictly Avoid Abbreviations

Never sacrifice clarity for brevity. Use description, not desc; use organizationId, not orgId. Clarity in API interfaces prevents hundreds of hours of debugging downstream.

🚀

Mindset: Design Before Programming

Regardless of whether you write your servers in Go, Node.js, Python, or Java, always dedicate a separate, language-agnostic interface design session first. Once the interface is rock-solid, coding the business logic becomes seamless.

The REST Masterclass Cheat Sheet

1. Roy Fielding's 6 Constraints

  • Client-Server: Strict separation of presentation (UI) from data storage and server logic.
  • Stateless: Every HTTP request contains all context needed. Zero server-side session memory between requests.
  • Cacheable: Responses must explicitly define cacheability (Cache-Control, ETag, max-age).
  • Layered System: Client cannot tell whether it is talking directly to the origin server or an intermediary proxy.
  • Uniform Interface: Resource URIs, representations, self-descriptive messages, and HATEOAS.
  • Code on Demand (Optional): Executable client scripts like JavaScript.

2. Methods & Idempotency Matrix

  • GET: Safe = YES, Idempotent = YES. Never mutates server data.
  • POST: Safe = NO, Idempotent = NO. Creates records or triggers custom domain actions.
  • PUT: Safe = NO, Idempotent = YES. Replaces entire resource representation.
  • PATCH: Safe = NO, Idempotent = NO (spec) / YES (standard field delta). Partial field update.
  • DELETE: Safe = NO, Idempotent = YES. Side-effect is identical: resource stays deleted!

3. The 4 Cardinal Rules of REST

  • Rule 1: Always Plural Nouns: Use /books, /books/:id (Never singular /book).
  • Rule 2: Lowercase & Hyphens: Use /order-items (Never camelCase /orderItems or underscores).
  • Rule 3: Sane Defaults: Always default page=1 and limit=20 with sorting created_at DESC.
  • Rule 4: Empty Collection is 200 OK: Never return 404 for an empty array! Always return 200 OK with data: [].

4. Custom Actions Pattern

When an operation is non-CRUD (e.g. archive, clone, send email, lock):

# Recommended: POST sub-resource action
POST /api/v1/organizations/:id/archive
POST /api/v1/projects/:id/clone
POST /api/v1/users/:id/send-verification-email

The REST specification treats POST as an open-ended sink for non-CRUD domain processes.

5. Status Code Cheatsheet

  • 200 OK: Successful GET, PATCH, or non-empty action.
  • 201 Created: Successful POST that created a new resource (returns Location header).
  • 204 No Content: Successful DELETE or action returning no body.
  • 400 Bad Request: Client sent malformed JSON or unparseable syntax.
  • 404 Not Found: Single resource ID does not exist in database.
  • 500 Internal Error: Uncaught backend exception or server failure.

6. Mindset: Interface First

Dedicate time to design your endpoints, URL routes, and JSON envelopes before writing SQL migrations or handlers. Clean standards guarantee zero guesswork, less bugs, and delightful frontend developer experiences.
